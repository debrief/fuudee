# Health check before the analysis-tools phase

7 Nov 2026. A wide survey of the whole repository at commit `97be7e3`, ranked by what will block the next phase: more analysis tools and more panels. Findings come with evidence and a one-PR remedy each; the fix plan at the end sequences them. No code was changed.

## Verdict

The substrate is sound and the test discipline is real, but the *way features are added* does not scale to a phase that adds many of them. Every operation since the first four tools has been bolted on by hand in four or five places (the RPC method tables, a 3,000-line catalogue class, a 3,000-line `activate()`, a second hand-written host for the playground, the flat message schema), and each of those places is also where the next panel will be bolted on. The cost shows already: pull requests average 69 files, the playground suite flakes on one part in ten runs, and `main` has no branch protection, so red checks do not stop merges.

The three changes that buy the most are a single registry for operations (Python), a host-neutral feature-registration layer shared by VS Code and the playground (TypeScript), and typed messages generated from LinkML instead of one 50-member bag. Everything else is either a consequence of those three or a process fix.

## Findings, ranked

Severity is impact on the next phase, not on today's users.

### 1. Operations are added by hand in four places; the tool framework that would make it one place is unused — High

`@tool` (`python/debrief-tools/src/debrief_tools/declare.py:66`) gives a tool a validated declaration, a generated input schema, worker isolation, provenance and conflict handling. Four tools use it. Every analysis operation since (TMA, cleaning, collation, sensors, track edits, narrative, figures) is instead a hand-written `debrief/*` JSON-RPC method: 65 of them in `service.py`'s `KNOWN_METHODS` (`python/debrief-tools/src/debrief_tools/service.py:275`). Those methods run in the service process rather than the worker, have no input schema, and are invisible to `tools/list`, so agent parity (TL-17) holds for four tools only.

Adding one method today touches the group tuples (`service.py:150-230`), `WRITING_METHODS`, `HISTORY_METHODS`, `KNOWN_METHODS`, the 150-line `_history` elif ladder (`service.py:520-640`), a per-group handler that re-dispatches on the method string, the module docstring, and the README. Parameter validation is hand-rolled `isinstance` checks repeated per branch; base-dict validation is duplicated verbatim in `service.py:536` and `worker.py:78`.

The README names about 30 of the 65 methods; `set_colour`, `edit_track`, `tma_*`, `find_jumps`, `mark_fix`, `take_new_data` and `resolve_ambiguity` are absent. The 90-line module docstring is the real reference.

**Remedy.** A `Method` descriptor (name, params model, reads or writes, handler) and one registry dict; register the existing groups through it; derive `tools/list`, the README's method table and the writing/history sets from it. Pydantic models for params already exist in the schema (`TmaRequest`, `TrackEdit`, `AnnotationSpec`).

### 2. `activate()` is one 3,160-line function and the playground has its own 4,053-line copy of it — High

`vscode/src/extension.ts:182` to `:3345` is a single closure: 116 top-level locals, 63 commands registered through a local helper, and cross-panel glue done by assigning callbacks onto panel objects (`map.previewed = …`, `coverageView.shown = …` at `:456-465`). No unit test imports it.

`vscode/play/host.ts` (4,053 lines) is a second extension host: its own `debrief.*` command table (`:2510`), its own Bearings pop-out (`:2114-2170`) mirroring `src/panels/bearingshost.ts`, its own copies of the flows that `webview/panels/flows/*` was meant to share. In the last 80 commits the two files are changed separately far more often than together, which is how parity drifts. Every new panel is wired twice, plus a view provider.

**Remedy.** Per-feature registration modules under `vscode/webview/panels/flows/` driven by a small `Host` interface, called from both `extension.ts` and `host.ts`; start with TMA and Bearings, whose controller already needs nothing of VS Code. Add a unit test asserting both hosts register the same command set.

### 3. Boundary types for the service and the panels are not generated — High

PRN-04 says every boundary type comes from LinkML. Two boundaries do not.

- The JSON-RPC surface: `vscode/src/service.ts:20-120` hand-declares 22 interfaces for requests and results; the Python side answers with 54 ad-hoc `return {...}` dicts. Nothing ties the two, and `HistoryStep` at `service.ts:52` shadows the generated name. `schemas/vectors/service-methods.json` lists method names only.
- Host-to-page messages: `WebviewMessage` is one class with 50 optional members and a 71-value `kind` enum (`schemas/linkml/messages.yaml:140-318`). Which members a kind needs lives in a parallel table, `MESSAGE_MEMBERS` (`documents.py:1048`), mirrored into `schemas/vectors/webview-messages.json` and read by `webview/messagecheck.ts:12`. The generated TypeScript is not a discriminated union, so pages cast (`message.tma as TmaView`, `webview/bearings.ts:55`) and hosts post `Record<string, unknown>`. A typo in a new panel's `show_*` kind is a runtime refusal, not a compile error. Page-side messages are not checked at all (`webview/vscode.ts:13`).

Layer-3 semantic rules are also duplicated: `ts/schemas/src/index.ts:5-7` says they are Python-only, yet `webview/messagecheck.ts:57-80` re-implements several "as Python's validation has them", and no test asserts the two agree on the 54 `invalid/semantic` message fixtures.

**Remedy.** One request and one result class per RPC method family in a new `rpc.yaml`; one class per message kind under an `any_of` union so json-schema-to-typescript emits a union; derive `MESSAGE_MEMBERS` from the schema and delete the vector; validate each Python reply against the generated JSON Schema in the service tests; run the TypeScript checker over the semantic fixtures and assert the same refusals.

### 4. `Catalogue` is a 3,092-line class with a hard-coded error whitelist — High

`python/debrief-stac/src/debrief_stac/catalogue.py` has about 70 methods across annotations, narrative, sensors, TMA, tracks, cleaning, collation, figures and views. Its single commit path, `_change`, catches a literal tuple of six domain errors (`catalogue.py:2273-2280`). A new domain module whose error is not added there escapes as a raw exception and reaches the extension as `-32603 Internal error` rather than a message for the analyst. Each domain re-implements "look up feature, apply, describe, build the record".

Error mapping in the service is equally flat: `CatalogueError`, `HistoryError`, `OSError` and `ValueError` all become `-32602 INVALID_PARAMS` (`service.py:617, :1348, :1382`), so a full disk, a locked store, damaged history and a bad parameter are indistinguishable to a panel that must decide whether to retry, re-open or show a form error.

**Remedy.** One `DomainError` base that all modules raise; move each domain's methods into its own module as functions `(plot) -> (changes, note, record)` and keep `_change` as the only commit path (it already has that shape); distinct RPC codes for retryable, re-open and invalid.

### 5. The playground suite is the flakiest check and nothing stops red reaching `main` — High

Of the last 100 CI runs, 30 failed; 28 of those only in `playground`, and 10 of the most recent 12 in part 3 alone (sensors, TMA, collation, export). Two were pushes to `main`. The 31 Oct `main` failure asserted a status-line regex after PR #87; the next push, touching only a dock file and two guides, passed. That is timing, not a regression. `main` has no branch protection (the protection endpoint returns 404), so a red check never blocks a merge. The five parts are hand-partitioned in `vscode/test/play/play.mjs:82-86`, so each new panel makes one part longer and flakier.

**Remedy.** Split part 3's TMA and sensor steps into their own part with explicit waits on the status line; have each `play*.mjs` export `{name, play, cost}` and shard by name so CI's matrix is generated; turn on branch protection requiring `schemas`, `vscode` and `playground`.

### 6. The tracer is one sequential script with no test boundaries, run twice — Medium

`vscode/test/integration/suite.ts` has no `test(` or `suite(` calls; `tracer()` (`:87-1632`) runs 54 screenshot steps in order under one 20-minute deadline. A failure at step 30 hides every step after it; nothing runs in isolation. CI runs it in VS Code 1.141 and 1.95 one after the other (`ci.yml:95-108`), making the `vscode` job the critical path at about 9 minutes; one branch logged a 178-minute run. Every new panel lengthens it.

**Remedy.** Mocha suites per feature sharing an `openSerial1()` fixture, one ordered smoke suite, a `DEBRIEF_IT_ONLY` filter; the two VS Code versions as a matrix sharing the build.

### 7. Adding a panel touches ten or more process surfaces by hand — Medium

PR #57 (TMA) changed 286 files: besides code, `site/mkdocs.yml`'s hand-listed nav, the interaction-model status table, a new model page, the glossary, keyboard equivalents, a blog post with six images, `vscode/package.json`, `vscode/README.md`, three play scripts, the SRD and the plan. The playground's panel list is hard-coded in `vscode/play/index.html`, and 21 blog posts name panels in `data-demo` attributes. Nothing checks these agree.

Related: each `WebviewViewProvider` copies the same lifecycle boilerplate (`timeview.ts:56-85`, `toteview.ts:89-121`, `coverageview.ts:67-82`, `timelineview.ts:77-90`, `map.ts:93-109`, `form.ts:33-42`, `results.ts:18-38`): options, HTML, ready flag, dispose, startup marks, "post only if ready". `retainContextWhenHidden` is set per panel in `extension.ts:467-471`; Form and Results lack it and have no `getState` fallback, so a tool form loses typed values when hidden. The map polls readiness every 100 ms up to 100 times (`map.ts:163-181`). Pop-out exists only for Bearings and is implemented three times.

**Remedy.** A `WebviewHost` base owning ready-gating, posting, startup marks and retention, with a `whenReady()` promise; a `PoppableView<Controller>` generalised from `BearingsHost`; directory-driven nav for the guides; a `check-panels.mjs` that cross-checks panel ids, `data-demo` names and tours so a missing registration fails CI.

### 8. Schema bumps rewrite about 170 fixture files and old files cannot be opened — Medium

Version strings are hard-coded in fixtures; the 0.0.24 commit touched 192 fixture files. The version moved 0.0.19 to 0.0.24 in nine days, yet about ten message-only changes since 25 Oct were folded into 0.0.24 without a bump, so "bump per change" is honoured for file types only, and there is no bump script. Both languages open an exact version match only (`documents.py:92-110`, `ts/schemas/src/index.ts:60-75`); every CHANGELOG entry repeats "plots must be imported or built again", only the newer-file direction is tested, and there is no migration hook. In a phase where each new tool may add a feature property, every release will refuse every existing plot, including the sample catalogue and colleagues' files.

Hand-written fast-path validators mirror generated types (`_plain_narrative`, `_plain_cut`, `documents.py:197-286`); only narrative has a guard test. Adding a document kind is a five-file chore across both languages with no test that the two lists match.

**Remedy.** A `scripts/bump_schema.py` that edits the schema, CHANGELOG stub and every fixture and sample; a stated rule that message and request changes do not bump the file version; read same-major-minor with patch at or below current through an (initially empty) migration registry; an older-version fixture test in both languages.

### 9. Provenance is optional for hand edits but mandatory for tools — Medium, correctness

`tools/call` refuses a call without `agent` (`service.py:1456-1466`, SUB-24). Every `debrief/*` write instead goes through `_agent()`, which silently defaults to `{"kind": "person", "name": "analyst"}` (`service.py:1630`). An agent that calls `debrief/edit_track` or `debrief/tma_create` leaves a record attributed to the analyst. No test covers it.

**Remedy.** Make `agent` required for every writing method; one test.

### 10. Service tests and unit tests carry costs that compound per panel — Medium

The service `client` fixture spawns a worker process per test, about a second each; the 166 service tests take 80 s. `test_entries.py:33` builds the whole sample catalogue through a subprocess to test a 20-line module. `test_tote_latency` asserts a p99 budget on shared hardware. On the TypeScript side 14 `toBeLessThan(ms)` assertions sit in unit tests; one reviewer saw `coverage.test.ts:55,76` fail under load, and the clean run here passed. The largest webview controls (`map.ts`, `tmacontrol.ts`, `timelinecontrol.ts`, `trackmap.ts`, `mapedit.ts`, `sensormap.ts`, `coveragecontrol.ts`, `totecontrol.ts`) have no unit tests; their DOM halves are covered only by the slow suites.

**Remedy.** Session-scoped worker with a per-test catalogue; a tiny fixture plot for `test_entries`; performance budgets behind an opt-in flag; a jsdom vitest project for the `*control.ts` classes, splitting `drawPlot` (510 lines, `tmacontrol.ts:1095`) into pure layout plus draw.

### 11. The delivery plan is a decision log, and the docs say the wrong thing is authoritative — Medium

`docs/delivery-plan.md` is 580 lines; "Open decisions and risks" runs from line 181 to 570, a chronological list of over 100 ticked items with paragraph-long test inventories. The phase tables have no open boxes and nothing says what is next. 67 of 307 commits touch the file. The two existing decision logs show the intended shape. `docs/README.md` claims the live Claude Docs are the source of truth, while the repository copies have been the working documents since mid-October (see "What was run").

**Remedy.** Move lines 181 to 570 into `docs/decision-log-2026-10.md`; leave the plan with phases and a "Next: analysis tools" section; fix the README claim; re-export to the live docs or retire them.

### 12. Stated rules with no enforcement, and pull requests too large to review — Medium

The PR template has nine checkboxes and nothing reads them; no CODEOWNERS or required reviewer; "each guide has one named owner" (plan line 29) names none. Across 59 merged PRs the mean is 69 files and 3,208 lines, median 26 files and 1,508 lines; 16 PRs have 100 or more files, mostly regenerated fixtures. 25 of 84 merge commits are `main`-into-branch syncs. The review copy on Heroku is never built by CI, and VS Code's version is pinned in three unrelated places (`review.Dockerfile:18`, `ci.yml:94`, `ci.yml:107`).

**Remedy.** A small checklist job that fails on unticked pairs; `.gitattributes` marking `schemas/fixtures/**` and `**/generated/**` as generated so reviews show the real change; a per-PR cap of one tool or one panel; a `review-image` CI job that builds the Dockerfile without pushing; one `VSCODE_VERSIONS` block.

### Lower

- `figures.py` imports `RpcError`, `INVALID_PARAMS` and `_agent` from `service.py` inside functions and reaches into `service._store` and `service._config` (`figures.py:143-200`). It is the template the next module will copy. Move the RPC plumbing to `debrief_tools/rpc.py`.
- Config is re-read and catalogues re-opened on every call (`service.py:470`; `Catalogue.open` eight times in `service.py`); collation opens every configured store per call. Panels that poll will multiply this. An mtime-keyed cache.
- The TypeScript "kernel" holds units, formatting, positions and figure IDs (512 lines); the mirrors of sensors, TMA, dead reckoning and intervals live in `vscode/webview/*.ts`, untestable without the extension's setup and unreachable from a future web host. Move the vector-consuming pure functions into `ts/kernel`.
- `CONFIG_VERSION = 4` is duplicated in both languages and not in the schema. `registry.for_selection` is an unused second implementation of `entries.offered_tools`. `escapeHtml` exists twice. `spikes/tote-latency` is referenced by nothing. Generated Pydantic enum names like `mSOLIDUSs` are never used, so the enum type is decorative.
- `vscode/README.md:70` lists TMA under "Not yet" while the same file describes it as shipped.
- Accessibility markers are dense in the time and TMA controls and absent from the results table; only one test asserts on roles.
- The preview workflow rebuilds the playground for nearly every PR and pushes to two branches that grow without bound.

## Strengths worth keeping

- Generation is honest: both generators run with `--check` in CI, the cross-language round trip covers 129 documents, 414 fixtures across 11 kinds are held to in both languages, and 17 shared vector files give bit-identical kernel behaviour.
- The tool contract (`run.py`) and history integrity (chain hashes, atomic rename, short locks, forged history can only make a plot read-only) are coherent and well tested.
- Redaction logging (NFR-14) with cross-language vectors is unusually disciplined.
- The guide rules are mechanised: `check-language.mjs` reads the language guide's own table, `check-theme.mjs` bans hard-coded colours, and both are green.
- The playground suite really plays every demo under CSP with message validation, and PR previews with screenshots land in the PR automatically.
- Zero reverts in 307 commits; spike write-ups state question, method and verdict.

## Method

Four parallel read-only reviews (Python workspace; VS Code extension and playground; schemas and shared libraries; process and infrastructure), each ranked for the next phase, then the High findings were re-verified by hand against the files cited. Every CI job was reproduced locally. The live Claude Docs were exported and diffed against the repository copies.
