# Debrief v4 — Delivery Plan (Draft)

Oct 8, 2026 · @Ian Mayo

## Purpose and basis

This plan sequences delivery of the SRD (Debrief v4 Software Requirements Document, revision 91) in six phases, substrate first. It replaces the build sequence in `tracer-delivery-plan.md` and the milestone order in `REIMPLEMENTATION_ORDER.md`, both written before the SRD's architecture was settled.

It keeps two things from them: the tracer plan's schema test strategy (golden fixtures, round-trip tests, schema comparison), and the milestone order's dependency analysis within capabilities (clean tracks before sensors, sensors before TMA). Phases carry no dates; durations need estimating once the Phase 0 spikes report. Identifiers (SUB-, CAP-, DEV- and so on) refer to the SRD.

## Planning principles

- **Substrate before capabilities.** The SRD's section 5 is shared and domain-neutral; nothing community-specific starts until it stands (SRD 12.1: the shared core covers roughly the first year).
- **Risks measured early.** Questions that decide architecture (Tote latency, Pyodide compatibility, LinkML fit) are answered by spikes in Phase 0, not discovered in Phase 3.
- **Vertical slices, each demonstrable and blogged.** Every phase ends in something a stakeholder can see working, with a blog post written in the same pull request (DEV-02, DEV-03, DEV-05).
- **Practice before pixels.** The style guide, interaction models and formatting service exist before the first graphical feature (DEV-10, SUB-04).
- **Breadth last.** REP and .dpf first; other formats arrive later as importer tools (EXT-02).
- **Community work runs as two streams.** Once the core stands, D and O/N work proceed in parallel; their relative priority is a strategic choice (SRD 12.3).

## Supporting guides

The style guide, interaction models and tool-author guide start thin and grow with the code. Each version 0 is drafted from material that already exists; after that, a guide is extended in the same pull request as the feature that needs it, and published on the GitHub Pages site beside the blog with the same sensitivity check (DEV-05).

| Guide | Version 0 drawn from | Grows in |
| --- | --- | --- |
| Style guide: language | DOMAIN\_GLOSSARY.md, SRD terms, SUB-04 formatting defaults (Zulu time, units, position notation) | Every pull request adding user-facing text |
| Style guide: theme | VS Code theme tokens; legacy data-colour conventions such as red and blue tracks, reviewed by analysts | Phase 1 onwards |
| Style guide: UI | VS Code UX guidelines, the vscrui component inventory, codicons | Phase 1 onwards |
| Interaction models | The SRD requirements each pattern cites | Phase 1: selection and tool offering, tool invocation and forms, unavailable capabilities. Phase 2: undo, conflicts, long-running operations, check overrides. Phase 3: keyboard equivalents |
| Tool-author guide | The team's experience writing its first tools | Drafted in Phase 1; tested by a scientist in Phase 5 |

Each interaction model is one short page: the requirements it cites, a Mermaid sequence diagram, and a pointer to its reference implementation. Each guide has one named owner. Lint checks for terminology and theme-token use are built in Phase 1, and analysts review the data-colour palette and the Phase 1 interaction models.

### Keeping the guides coherent

Guides that grow one pull request at a time risk three failures: entries appended rather than placed, locally reasonable choices that contradict each other, and guides that each hang together but disagree with one another. Three measures guard against them.

**A skeleton.** Version 0 of each guide defines every top-level section, including empty ones marked with the phase that will fill them. New material goes into a known place; material that fits nowhere is flagged at review as either new territory or out of scope.

**A North Star.** One shared statement, derived from the SRD's North Star and principles, with a sharper line for each guide. Each must be concrete enough to settle a disagreement. The drafts below are for the team to refine in Phase 0.

| Guide | North Star (draft) |
| --- | --- |
| All guides | An analyst who has learned one part of Debrief can predict the rest. |
| Style guide: language | Say what an analyst would say: plain British English, glossary terms, never software jargon. |
| Style guide: theme and UI | Look native to VS Code; keep colour for what the data means. |
| Interaction models | Predictable and forgiving: the same gesture does the same thing everywhere, and nothing is silent or irreversible (SUB-21, SUB-28). |
| Tool-author guide | A scientist's first tool should take an afternoon. |

**Two mechanisms.** Every entry cites the principle it serves; an entry that cannot is a warning sign. Each guide's owner reads it end to end at every phase exit, resolving contradictions while they are few.

- [x] 15 Oct 2026, product owner: out-of-order "times" are text. Importing a track asks whether it is plotted over the ground (OTG, positions as logged) or by dead reckoning (DR, from the first fix by each fix's course and speed), with *Use this choice for future imports*: a community tends to stick with one, so once chosen Debrief asks no more, and the import's notes say which mode was used and how to change it. The mode is kept on the track, as content recorded in history, and changing it later is one undoable step; a track plotted DR keeps its positions as logged so OTG can put them back. Agents and tests pass the mode. DR places each fix from the one before by that fix's recorded course and speed, along the geodesic: on legacy sample plots this reproduces the positions legacy saved for DR legs to within 0.1 m. A .dpf plot says how each leg was plotted (PlotRelative), so it is not asked; a DR leg comes with only the positions legacy worked out, so it cannot be plotted over the ground, and the import says so (CAP-01, EXT-14, EXT-15). (14 Oct)

- [x] 14 Oct, product owner: the remembered OTG or DR choice is user state, and must be clearable. It is a three-way setting, ask (the default), otg or dr, held in the user-settings layer (debrief-config, the same in Python and TypeScript), never in STAC: not in a catalogue, an item or a plot file. In VS Code it is the setting **Debrief: Track import mode**, kept in step with the analyst's Debrief configuration, and **Debrief: Ask again whether imported tracks are OTG or DR** clears it; in the playground it is the page's own settings, with **Ask again** under *Import*. The host reads it and passes the mode to the importer, which never reads user state itself (CAP-01, SEC-06). (14 Oct)

- [x] 14 Oct, product owner: editing a track plotted by dead reckoning. On a DR track the truth is its origin (where its first fix is) and each fix's course and speed; its positions are always worked out again by dead reckoning, and never moved on their own. A move of the whole track moves the origin; every other operation changes courses and speeds: a rotation adds its angle to the courses of the fixes in the period (each the leg from that fix, so the leg out of the period's last fix too), a stretch scales their speeds, a shear adds one set and drift to them so the dragged end lands where it was dragged (on a straight leg, exactly the course and speed the readout shows; a period with turns keeps them), smoothing averages courses and speeds, and a single fix dragged changes the leg into it so dead reckoning puts it where it was dropped, every later fix following. The fixes after a period follow on: no jump, and the readouts and steps say so in dead-reckoning terms (*RED ONE (DR) leg into 09:43:00Z now 056.5°T 12.1 kn*); the map previews the dead-reckoning result, checked against the tool service by shared test vectors. Decided with it (14 Oct): jumps on a DR track are fixes whose logged speed is wild (in short runs, never the first or the last fix), removed by letting the leg before carry on to the fix after, rather than refusing jump removal; the positions, courses and speeds as logged are all kept beside the track, so the check before plotting it over the ground again compares origin, courses and speeds with them (a rotation is now caught) and over the ground puts all three back; plotting a track DR starts from its data as it is, which over the ground is its logged data; merged DR tracks follow on from one origin. Step names may now be up to 64 characters in the History view. (CAP-01, CAP-21; schema 0.0.17 gains `logged_courses` and `logged_speeds`.) (14 Oct)

- [x] 14 Oct, product owner: relative bearing stays as built. It is measured from the primary's course, not a separate heading, and written red to port and green to starboard, `R045.0°`, `G120.0°`; dead ahead `000.0°` and dead astern `180.0°`, with no side. - [x] 14 Oct, product owner: angle on the bow and bearing rate are core measures, not left to study groups. Angle on the bow is the secondary's aspect as the primary sees it: the bearing from the secondary to the primary less the secondary's course, written red or green as relative bearing is (`R030.0°`, `G135.0°`). Bearing rate is the rate of change of the true bearing from the primary to the secondary, from both tracks' courses and speeds at current time, in the angular-rate quantity kind and the analyst's units (`°/min`), positive drawing right (clockwise), as the formatting service writes every angular rate. Both are worked out in Python with the other measures; the views only format them. In a narrow Tote they are labelled under the range, bearing and relative bearing columns, with the track's own measures, so the layout stays one row of headings (CAP-06, CAP-07); that layout was superseded the same day by legacy Debrief's table, below. (14 Oct)

- [x] 14 Oct, product owner: the Tote is legacy Debrief's table, a row a measure and a column a track. Seen on a phone, the labelled layout (the primary's values as labelled fields, then for each secondary a name, a line of values under headings and two more lines of labelled values, units in every cell) was ugly: "with table headings you don't need labelled fields". It is replaced by one layout at every width. The first column holds the row headings, one a measure, each with the unit its values are in, as the analyst's settings write it and taken from the formatter so the two cannot disagree: `Range nmi`, `Brg °T`, `Rel °`, `AOB °`, `Brg rate °/min`, `Crse °T`, `Spd kn`, `Depth m` (`Range yd`, `Spd m/s`, `Depth ft` and so on with other settings). Relative bearing and angle on the bow carry `°` in their headings, so their cells, like every other, hold figures only (`R024.5`). A value in a unit other than its heading's keeps its own: a close range is `1070 yd` in a row headed `nmi`, the one cell where a unit appears, which reads plainly and needs no footnote. Then the primary's column, its name in bold, blank for the measures between tracks; then a column a secondary, its colour, name (breaking at its spaces onto a second line where room is short, so a column is no wider than its values; cut short beyond that, in full on hover) and **×** (named "Remove Cargo 01 from the Tote" for screen readers; `Delete` on it too) in its heading. Values are right-aligned in tabular figures, with one quiet rule where the measures between tracks give way to each track's own. Where the columns do not fit (a sidebar, the playground's side column, a blog demo, a phone), the row headings stay put and the tracks scroll sideways inside the table, never the page. A track with no data at current time has a column of dashes and says why under the table (*Tug 01 Ended 10:35:17Z*), where a phone can read it. While playing, values are written into the cells already there, so nothing moves and keyboard focus stays. A real `table` (`aria-label` "Tote", `th scope="row"` and `scope="col"`) (CAP-06, NFR-13). (14 Oct)

- [x] 14 Oct, product owner: course across a reversal. Where the recorded courses at the fixes either side are opposite, within 0.5°, the Tote does not interpolate (there is no shorter way round, and half way is a course never steered) but gives the nearer fix's course in time, the later one's exactly half way. Python's `TrackMotion` does it; the map interpolates no course. The shared track-position vectors gain recorded courses and the course expected at each sample, reversals and a 179° turn among them (CAP-06). (14 Oct)

- [x] 14 Oct, product owner: the map shows the Tote, subtly. A thin dashed line in a muted theme colour (never a fixed one) from the primary to each secondary at current time, along the geodesic, moving with current time; a box in the Tote, **Lines on the map**, turns the lines off and on. Whether they show is island state with the choice of tracks (`ToteView.map_lines`, left out meaning shown): never a step, never undone (CAP-06, SUB-22). (14 Oct)

- [x] 14 Oct: the Tote's choice of tracks is view state, in the plot's island. Which tracks the Tote compares (the primary, the secondaries and the measure group) is how the plot is being looked at, not a change to it, so it follows the product owner's reasoning for the time window (12 Oct): it travels with the plot file, so a colleague opens the same Tote, but it is never a step in the history, never undone by `Ctrl+Z`, never in provenance, and never conflicts with a change to content; a colleague's choice made meanwhile is shown, never overwritten (SUB-28). Legacy Debrief kept its Tote's tracks in the GUI part of a .dpf file, beside the data, for the same reason. Tracks chosen that the plot no longer has are shown as missing, not refused, since a change to content never changes the island (CAP-06, SUB-22). (14 Oct)

- [x] 14 Oct: the Tote's core measures and latency. The core measure group is legacy Debrief's Tote: range, bearing (true) and relative bearing from the primary to each secondary, and each track's course, speed and depth; legacy's optional angle on the bow and bearing rate are left to study groups (superseded the same day by the product owner: both are core, below). Each track is placed at current time exactly as the map places its marker (along the geodesic between the fixes either side, in proportion to time; shared test vectors hold Python and the map to it); course, speed and depth are the recorded values interpolated the same way, course the shorter way round through 360°, or from the positions where none were recorded. Relative bearing is from the primary's course, written red (port) or green (starboard), `R045.0°`, `G120.0°`. Values travel in SI units and are written by the formatting service with the analyst's settings; depths in metres (feet where lengths are imperial) to one decimal, until a depth setting exists. One request per change of current time, never queued (the latest time when the previous answer arrives), measured at p95 9 ms in VS Code through the tool service and 15 to 33 ms in the playground under Pyodide, against 100 ms: the dense-sampling fallback stays a contingency, not built (CAP-06, CAP-07, NFR-04). (14 Oct)

- [x] 13 Oct, product owner: annotations through forms first. Shapes, labels and notes are added, changed, restyled and deleted through a form (and the same tool-service methods for agents and the playground), each as one recorded, undoable step named in the History view. GeoJSON has no curves, so a circle or an ellipse is a polygon of 72 sides along geodesics, for other tools and for the plot's extent, with its exact centre and size as properties, from which Debrief draws and edits it.
